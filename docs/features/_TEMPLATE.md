## 1. What is implemented today

A table or list of the surface, with **evidence per row** — a file and line, or a commit. This is
the section a reader comes for, so it goes first.

State each row as implemented or not. Where behaviour is surprising, say so here rather than
leaving it to be discovered.

> **Why evidence per row:** `docs/` has carried claims that outlived their code — a battery
> recorded as still owed that had existed for two days, a render field described as needed that
> both mixers already had. A line reference is checkable in seconds; prose is not.

## 2. How to drive it

Every command with its real parameter list, taken from `AMCPCommandsImpl.cpp` rather than from
another document, and at least one **runnable** example per command.

```
MIXER 1-1 EXAMPLE_COMMAND 1.0 0.6 0.25
```

Config elements too, if any, with their defaults — and the defaults must match the commented
reference block at the bottom of `src/shell/casparcg.config`, which is where an operator looks to
find out an option exists at all.

**Asymmetric values in examples wherever a per-channel quantity appears.** An example that sets
equal R, G and B is invariant under a red/blue exchange, so it demonstrates nothing and cannot be
copied into a test that discriminates. This is not hypothetical: it is how the ICVFX gain defect
survived.

## 3. Design decisions, and what they cost

Only decisions that constrain a future change. For each: what was chosen, what was rejected, and
the evidence. A decision with no alternative recorded is a description, not a decision.

Where a fast path and a correct path differ, say which this is. Where an approximation is used,
name it as one — `CLAUDE.md` records a gamut compressor labelled as the ACES reference in three
places while measuring 0.350 max from it.

## 4. Verification — what is measured, and what is not

| what | battery | numbers | date |
| :--- | :--- | :--- | :--- |

**And immediately, in the same section: what these numbers do NOT cover.** A figure without its
limits reads as a stronger claim than it is. `LED_CALIBRATION.md` says 32/32 at 1 LSB and then
says, in the next sentence, that only the IMAGE consumer was captured and only one layer
composited — so a reader takes it as "the LUT is applied correctly" rather than "`CALIBRATION`
works".

If a battery exists but **cannot fail** for this feature, that belongs here and not in a footnote.
`vk-validation` reported clean for a deliberately planted VUID; a green run from it is not evidence.

## 6. Related commits

Newest first, one line each, with *why the commit matters* rather than its subject line repeated.
This is the section that makes `git log` navigable a year from now — and it is the section a
reader uses to find the reasoning that did not fit anywhere else.

## 7. Diagrams

Per `CLAUDE.md`: **operator-facing manuals get a rendered PNG** generated by a script in
`docs/diagrams/` and committed to `docs/images/`, so the markdown renders with no build step and
the diagram stays reviewable as source. **Developer and architecture notes get inline mermaid**,
so they diff as text and change in the same commit as the code.

A feature earns a diagram when its **order** is the point, when **two paths reach the same place**,
or when a stage's **position** is the whole feature. Not otherwise — keep them to the stages and
the branch, never every uniform.
